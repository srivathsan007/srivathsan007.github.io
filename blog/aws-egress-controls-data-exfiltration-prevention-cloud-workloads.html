AWS Egress Controls and Data Exfiltration Prevention for Cloud Workloads

Most cloud data leaves through paths nobody deliberately opened. Egress control is the difference between a contained incident and a breach notification — here is how to build it in layers that survive a compromised credential.

Egress is the control nobody budgets for

The asymmetry that matters

Ingress controls decide whether an attacker gets in. Egress controls decide what it costs you when they do. Almost every security programme is heavily weighted toward the first.

Walk into most cloud security reviews and you will find a detailed story about ingress. Security groups are tight, WAF rules are tuned, and the load balancer terminates TLS with a modern policy. Then ask a simple question: if this workload were compromised right now, where could the data go?

The answer is usually anywhere. A private subnet with a NAT gateway and a default route to 0.0.0.0/0 can reach every endpoint on the internet. The instance profile can call S3. The application already holds database credentials. Nothing in that path distinguishes a legitimate API call from a bulk copy to an attacker-controlled bucket.

This is the asymmetry worth internalising. Ingress controls are probabilistic — they reduce the chance of compromise. Egress controls are structural: they bound the damage of a compromise that already happened. Credential theft, a vulnerable dependency, a malicious package in your build, an over-permissioned CI role — all of these end in the same place, which is data moving outward. Egress is the last place you can still intervene.

VPC endpoints: take the internet out of the path

The first layer is to stop routing AWS service traffic across the public internet at all. Gateway endpoints for S3 and DynamoDB, and interface endpoints for everything else, keep that traffic inside the AWS network.

But the routing change is the smaller half of the benefit. The control is the endpoint policy. A default endpoint policy allows all actions on all resources, which means you have improved latency and egress cost without meaningfully constraining an attacker. A restrictive policy changes the calculus:

  • Scope s3:GetObject and s3:PutObject to the specific bucket ARNs the workload legitimately uses
  • Deny writes to any bucket outside your organisation using the aws:ResourceOrgID condition key
  • Pair the endpoint policy with aws:PrincipalOrgID so stolen credentials from another tenant cannot be used through your endpoint

The result is that a compromised workload holding valid credentials still cannot copy your data into an external bucket, because the network path to that bucket does not exist and the endpoint policy would refuse it even if it did. That is a control that survives credential theft, which is the bar every egress control should be measured against.

Network Firewall and DNS: control the names, not just the addresses

Do not forget DNS

Domain allowlisting with Route 53 Resolver DNS Firewall closes the channel where data is smuggled inside DNS queries themselves — a path that IP-based rules never see.

Workloads need to reach things that are not AWS services: package registries, partner APIs, telemetry endpoints. Blanket internet access for this is the default, and it is the gap.

AWS Network Firewall lets you replace that default with a domain allowlist. Stateful rule groups inspect the TLS SNI and HTTP Host header, permit the names you have approved, and drop everything else. Run it in strict order evaluation so an explicit allow is genuinely required rather than inferred.

Route 53 Resolver DNS Firewall handles the layer underneath. This matters more than it first appears, because DNS is itself an exfiltration channel — data encoded into subdomain labels and queried against a nameserver the attacker controls. Traffic like that never opens a TCP connection your network rules would inspect. Domain-level blocking, combined with query logging, is what closes it.

Together these give you a defensible statement: this workload can resolve and reach exactly these names, and every attempt to reach anything else is denied and recorded.

Service Control Policies: guardrails that outrank IAM

Network controls assume the attacker is operating inside your network path. An attacker with a stolen role can operate from anywhere, against the AWS API directly. That is what organisation-level guardrails are for.

Service Control Policies apply at the AWS Organizations level and cap what any principal in an account can do — including administrators. No IAM policy can grant a permission an SCP denies, which makes this the one layer that still holds when identity itself is compromised.

The egress-relevant patterns are worth applying deliberately:

  • Region restriction. Deny all actions outside the regions you operate in. Attackers frequently stage data in unused regions precisely because nobody is monitoring them.
  • Organisation boundaries. Use aws:ResourceOrgID to deny S3 writes and snapshot copies to destinations outside your organisation.
  • Sharing primitives. Deny the APIs that make data public — disabling account-level S3 Block Public Access, sharing AMIs, RDS snapshots or EBS snapshots externally.
  • Protecting the evidence. Deny cloudtrail:StopLogging, guardduty:DeleteDetector and their equivalents so an attacker cannot disable detection before exfiltrating.

That last one is routinely forgotten. Controls that an attacker can switch off are not controls.

Detection: prove the controls are doing something

A blocked connection is only useful if someone learns from it. The detection layer turns your egress controls from a static wall into a signal source.

GuardDuty already produces findings shaped exactly like this problem — Trojan:EC2/DNSDataExfiltration, Exfiltration:S3/ObjectRead.Unusual, UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration. Route the findings into Security Hub for aggregation, then use EventBridge rules to act on the severities that justify action.

The pieces worth wiring up:

  • VPC Flow Logs and Network Firewall alert logs into a queryable store, so you can answer what did this host talk to during an investigation
  • Resolver DNS Firewall query logs, which are frequently the earliest signal of compromise
  • Automated response for high-confidence findings — isolating an instance by swapping its security group is a reversible action worth automating

Instrument before you enforce. The logs from alert-only mode are what tell you which legitimate dependencies you were about to break.

Rolling this out without breaking production

Sequence matters

Observe, then allowlist, then enforce, then narrow. Teams that jump straight to enforcement generate an outage, lose organisational trust, and the project gets shelved.

The technical design is the easy part. The reason egress control programmes fail is sequencing — they get deployed as a big-bang change, break a deployment pipeline on day one, and never recover politically.

A staged rollout that works:

  • Observe. Turn on VPC Flow Logs, DNS query logging, and Network Firewall in alert-only mode. Spend a few weeks building an accurate picture of real egress.
  • Allowlist from evidence. Build the domain allowlist from what you actually observed, not from what teams believe they depend on. The gap between those two is always instructive.
  • Enforce in one non-critical account first. Prove the control and the exception process on something that can absorb a mistake.
  • Expand by workload tier, starting with the accounts holding regulated or sensitive data, where the value is highest.
  • Narrow continuously. Treat the allowlist as something that shrinks over time, and make expiry the default for exceptions.

Pair this with a genuinely fast exception path. If the only way to unblock a legitimate dependency is a change ticket with a three-day turnaround, engineers will route around the control, and you will have traded real security for the appearance of it.

Key takeaways

  • →Inbound controls decide who reaches your workload. Egress controls decide how much a successful attacker can take. Only one of those limits blast radius.
  • →A VPC endpoint without an endpoint policy is a performance optimisation, not a security control — the policy is where the value lives.
  • →Service Control Policies are the only layer that still holds when an attacker controls a role with broad IAM permissions.
  • →Turn on logging and run in alert-only mode first. Egress controls break production when they are deployed blind.
  • →DNS is an exfiltration channel. If you allowlist domains but leave Resolver DNS Firewall off, you have left the side door open.
